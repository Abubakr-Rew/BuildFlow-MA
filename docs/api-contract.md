# BuildFlow API Contract

> Этот документ описывает контракт REST API, на который рассчитаны `ApiXxxRepository`-скелеты.
> Пока бэкенд не готов, приложение работает на `FakeXxxRepository` с демо-данными.

## Base URL

```
https://api.buildflow.kg/v1
```

## Authentication

Все запросы (кроме login/register) требуют заголовок:

```
Authorization: Bearer <token>
```

## Auth

### POST /auth/login

```json
// Request
{
  "email": "owner@buildflow.kg",
  "password": "123456"
}

// Response 200
{
  "token": "eyJhbGciOiJI...",
  "user": {
    "id": "user-1",
    "email": "owner@buildflow.kg",
    "name": "Асан Бекович",
    "role": "owner",
    "companyId": "company-1"
  }
}

// Response 401
{ "error": "Неверный email или пароль" }
```

### POST /auth/register

```json
// Request
{
  "email": "new@company.kg",
  "password": "secret123",
  "name": "Имя Фамилия",
  "companyName": "Новая Компания"
}

// Response 201
{
  "token": "eyJhbGciOiJI...",
  "user": { ... },
  "company": {
    "id": "company-2",
    "name": "Новая Компания"
  }
}

{ "error": "Пользователь с таким email уже существует" }
```

### POST /auth/join

Присоединение прораба или строителя по коду приглашения (`POST /team/invite`).
Роль и компанию задаёт код, клиент их не передаёт.

- Клиент отправляет код нормализованным: без пробелов и дефисов, в верхнем регистре (`abc-234` → `ABC234`).
  Сервер сравнивает так же.
- Код одноразовый. Сервер помечает его использованным в той же транзакции, в которой создаёт пользователя
  и участника компании. После этого новый участник есть в `GET /team/members`.
- Неизвестный, уже использованный или истёкший (`expiresAt` в прошлом) код → 404. Различать эти случаи клиенту
  не нужно: пользователь в любом случае просит у директора новый код.
- Занятый email → 409. Сервер проверяет его до того, как погасить код, поэтому тот же код можно отправить
  ещё раз с другим email.
- **Погашение атомарное.** Проверка «код есть, не использован, не истёк» и пометка `isUsed` выполняются одной
  операцией, например `UPDATE invites SET used_at = now() WHERE code = ? AND used_at IS NULL AND expires_at > now()`
  с проверкой числа изменённых строк, или под блокировкой строки в транзакции. Пользователь и участник создаются
  в той же транзакции. Из двух одновременных запросов с одним кодом успешен только один (201), второй получает 404.
  Если создать пользователя не удалось (например, email заняли параллельно → 409), транзакция откатывается
  и код остаётся неиспользованным.
- **Ограничение попыток.** Коды короткие (31⁶ ≈ 890 млн вариантов), поэтому подбор надо ограничивать: не больше
  10 запросов в минуту с одного IP и с одного устройства (заголовок `X-Device-Id`). Считаются все запросы, а не только
  неудачные. При превышении сервер отвечает 429 с заголовком `Retry-After` (секунды) и запрос не выполняет. Клиент
  показывает `tooManyRequests` («Подождите минуту») и сам повторно не отправляет.

```json
// Request
{
  "email": "worker@mail.kg",
  "password": "secret",
  "name": "Имя",
  "inviteCode": "K7M2QX"
}

// Response 201
{
  "token": "...",
  "user": {
    "id": "user-7",
    "email": "worker@mail.kg",
    "name": "Имя",
    "role": "worker",
    "companyId": "company-1"
  },
  "company": { "id": "company-1", "name": "СтройБишкек" }
}

// Response 404
{ "error": "Неверный, использованный или истёкший код приглашения" }

// Response 409
{ "error": "Пользователь с таким email уже существует" }

// Response 429, заголовок Retry-After: 60
{ "error": "Слишком много попыток" }
```

## Team

### GET /team/members

```json
// Response 200
{
  "members": [
    {
      "id": "member-1",
      "userId": "user-1",
      "name": "Асан Бекович",
      "email": "owner@buildflow.kg",
      "role": "owner",
      "companyId": "company-1",
      "assignedProjectIds": []
    }
  ]
}
```

### GET /team/members?query=&role= — поиск людей

Поиск по имени и фамилии. Параметры необязательные: без них ответ тот же, что у `GET /team/members`.
Формат ответа тоже совпадает.

- **Только своя компания.** Сервер ищет среди участников компании из токена. Параметра `companyId` нет,
  и людей других компаний ответ не содержит ни при каких параметрах.
- `query` обрезается по краям. Если он короче 2 символов, сервер не ищет и отвечает `200 { "members": [] }`.
  Клиент такие запросы не шлёт: при пустом запросе он показывает недавно открытых людей.
- `role` — `owner`, `foreman` или `worker`, сужает выдачу. С `role` и без `query` сервер отдаёт всех людей
  этой роли. Другое значение `role` → 400 (`validation`).
- `assignedProjectIds` в ответе на поиск содержит только объекты, которые видит вызывающий. Директору сервер
  отдаёт все объекты человека, прорабу и строителю — только общие. Названия чужих объектов не раскрываются.
- Сортировка по имени, не больше 50 человек.

Правила сопоставления те же, что в клиенте (`matchName` в `lib/features/team/domain/member_search.dart`):
клиент подсвечивает совпадения сам и должен находить то же, что сервер.
- регистр не учитывается;
- каждое слово запроса совпадает с началом какого-нибудь слова имени, разделители — пробел и дефис:
  «асан» находит «Бакыт Асанов», а «сан» — нет;
- ё = е; киргизские ң, ө, ү ищутся и по себе, и по н, о, у;
- латиница читается как кириллица («bakyt» → «Бакыт», «jumabekov» → «Жумабеков»). Чтобы латиница
  не была неоднозначной, при сравнении склеиваются й/ы/и и э/е.

Пока сервера нет, клиент фильтрует уже загруженный `GET /team/members` сам. На этот эндпоинт он перейдёт,
когда компании вырастут настолько, что держать всю команду в памяти станет дорого.

### POST /team/invite

Генерация одноразового кода приглашения (только owner). Кто присоединится по коду (`POST /auth/join`),
получит указанную роль в компании директора.

- `role` — только `foreman` или `worker`. На `owner` или любое другое значение сервер отвечает 400 (`validation`).
- Код: 6 символов из `ABCDEFGHJKMNPQRSTUVWXYZ23456789`. Похожих символов (0/O, 1/I/L) в нём нет: коды диктуют
  по телефону и перепечатывают из сообщений.
- Срок действия — 7 дней (`expiresAt`).

```json
// Request
{ "role": "worker" }

// Response 201
{
  "invite": {
    "code": "K7M2QX",
    "companyId": "company-1",
    "role": "worker",
    "createdAt": "2024-06-15T10:00:00Z",
    "expiresAt": "2024-06-22T10:00:00Z",
    "isUsed": false
  }
}
```

### DELETE /team/members/:id

Удаление участника из компании (только owner).

Сервер в той же операции убирает участника из `foremanIds` / `workerIds` всех объектов компании
и закрывает ему все чаты компании, включая личные (см. «Чат → Правила доступа»).
Клиент после 204 только перезагружает объекты и участников, отдельных запросов к объектам не шлёт.
Повторный `DELETE` уже удалённого участника → 404 (`notFound`).

Удалённый участник больше не может войти: `POST /auth/login` отвечает ему 401 (`invalidCredentials`). Его выданные
токены сервер отзывает, и следующий запрос с таким токеном, включая `POST /auth/restore`, получает 401
(`sessionExpired`). Клиент в ответ разлогинивает пользователя. В Fake-режиме это не реализовано: удалённый участник
по-прежнему входит.

```json
// Response 204 (no content)
```

## Чат

Клиент: `ChatRepository` (`lib/features/chat/domain/repositories/chat_repository.dart`). Fake-реализация —
`FakeChatStore`, она соблюдает все правила ниже.

### Правила доступа

- Сервер отдаёт чат, его историю и события только участникам чата. Не участник получает 403 (`forbidden`),
  несуществующий чат — 404 (`notFound`).
- **Чат объекта** (`type: "project"`) создаётся вместе с объектом. Его участники — команда объекта:
  все директора компании плюс `foremanIds` и `workerIds` объекта. Состав чата меняется в той же транзакции,
  что и состав объекта (`PUT /projects/:id`, `POST/DELETE /projects/:id/foremen`). Для каждого добавленного
  и убранного человека сервер пишет системное сообщение (`kind: "system"`).
- Исключённый из объекта сразу теряет чат: `chat.removed` по WebSocket, чат пропадает из `GET /chats`,
  запросы к нему → 403. Новые сообщения ему не рассылаются. Если его вернут в объект, он снова видит всю историю.
- **Личный чат** (`type: "direct"`) — только между двумя людьми одной компании, создаётся по требованию
  (`POST /chats/direct`). Писать самому себе нельзя.
- **Удалённый из компании** (`DELETE /team/members/:id`) теряет доступ ко всем чатам компании, включая личные:
  он пропадает из участников чатов объектов (с системным сообщением), его токены отозваны. Его личные чаты
  остаются у собеседников для истории, но писать в них нельзя: `POST /chats/:id/messages` → 403.
- Пользователь видит только чаты своей компании.

### GET /chats

Чаты пользователя, последние по активности первыми. `title` — название объекта у чата объекта, у личного
пустая строка: имя собеседника клиент берёт из `GET /team/members`. `unreadCount` и `lastMessage.status`
посчитаны для вызывающего.

```json
// Response 200
{
  "chats": [
    {
      "id": "chat-project-1",
      "type": "project",
      "projectId": "project-1",
      "title": "ЖК «Ала-Тоо Резиденс»",
      "participantIds": ["user-owner-1", "user-foreman-1", "user-worker-1"],
      "updatedAt": "2026-10-28T09:41:00Z",
      "unreadCount": 2,
      "lastMessage": { "id": "msg-812", "clientId": "…", "chatId": "chat-project-1", "senderId": "user-foreman-1",
                       "kind": "text", "text": "Хорошо, к 17:00 будет отчёт.", "createdAt": "2026-10-28T09:41:00Z",
                       "status": "sent", "attachments": [] }
    }
  ]
}
```

### GET /chats/:id/messages?before=&after=&limit=

История, всегда от старых к новым.

- Без `before` и `after` — последние `limit` сообщений.
- `before=<messageId>` — до `limit` сообщений старше указанного (прокрутка вверх). Меньше `limit` в ответе
  значит, что история кончилась.
- `after=<messageId>` — все сообщения новее указанного, но не больше 500 (догрузка после переподключения).
  Если пропущено больше, сервер отдаёт последние 500 и `"truncated": true`, клиент тогда перезагружает чат.
- `limit` — 1–100, по умолчанию 50. Неизвестный `messageId` → 404.

```json
// Response 200
{ "messages": [ { "id": "msg-811", … }, { "id": "msg-812", … } ], "truncated": false }
```

### POST /chats/:id/messages

Отправка. `clientId` генерирует клиент (uuid v4) и повторяет его при каждой попытке отправить то же сообщение.
Сервер хранит пару (отправитель, `clientId`) и на повтор отвечает **200 с уже созданным сообщением**, второй
копии не будет. Так безопасно повторять запрос после таймаута, когда неизвестно, дошёл ли первый.

- `kind` на этапе 1 — только `text`. `text` обрезается по краям, длина 1–4000, иначе 400 (`validation`).
- Отправка отмечает чат прочитанным отправителем до этого сообщения.
- Не больше 30 сообщений в минуту от одного пользователя, сверх — 429 (`tooManyRequests`).

```json
// Request
{ "clientId": "1b9d6bcd-bbfd-4b2d-9b5d-ab8dfbbd4bed", "kind": "text", "text": "Бетон привезли" }

// Response 201 (создано) или 200 (повтор с тем же clientId)
{ "message": { "id": "msg-813", "clientId": "1b9d6bcd-…", "chatId": "chat-project-1", "senderId": "user-foreman-1",
               "kind": "text", "text": "Бетон привезли", "createdAt": "2026-10-28T09:45:12Z", "status": "sent",
               "attachments": [] } }
```

### POST /chats/direct

Личный чат с человеком: существующий (200) или новый (201). Повторный вызов дубль не создаёт, порядок
пары не важен. `userId` равен своему → 400 (`validation`). Человек не из своей компании или не существует → 404.

```json
// Request
{ "userId": "user-foreman-1" }

// Response 200 / 201
{ "chat": { "id": "chat-…", "type": "direct", "participantIds": ["user-owner-1", "user-foreman-1"], "title": "", … } }
```

### POST /chats/:id/read

Отметка «прочитано до сообщения включительно». Отметка только двигается вперёд: более старый `upTo` ничего
не меняет и тоже отвечает 204. Клиент шлёт её при открытии чата и на каждое новое чужое сообщение, пока чат открыт.

```json
// Request
{ "upTo": "msg-812" }

// Response 204
```

### Реальное время: STOMP поверх WebSocket

- Подключение: `wss://api.buildflow.kg/v1/ws`, кадр `CONNECT` с заголовком `Authorization: Bearer <token>`.
  Неверный или отозванный токен → `ERROR` и закрытие, клиент делает то же, что при 401 (`sessionExpired`).
  Heartbeat 10 000 / 10 000 мс.
- Подписка одна: `SUBSCRIBE /user/queue/chat`. Сервер шлёт в неё только события чатов, где пользователь
  участник, так что отдельных подписок на чаты нет.
- Тело кадра — JSON `{ "type": "...", ... }`:

| `type` | Поля | Когда |
|--------|------|-------|
| `message.created` | `chatId`, `message` | Новое сообщение, включая свои (с другого устройства) и системные |
| `message.status` | `chatId`, `upTo`, `status: "read"` | Кто-то другой прочитал свои сообщения пользователя до `upTo` включительно |
| `chat.updated` | `chat` (как в `GET /chats`) | Сменились `title`, участники, `unreadCount` или `lastMessage`; также новый чат |
| `chat.removed` | `chatId` | Пользователя исключили из объекта или из компании |

- Клиент применяет события по `id` сообщения идемпотентно: повтор `message.created` не создаёт дубля, а своё
  сообщение он сопоставляет с ожидающим по `clientId`.
- **Переподключение**: экспоненциальная задержка 1, 2, 4… до 30 с. После переподключения клиент делает `GET /chats`,
  а для открытого чата — `GET /chats/:id/messages?after=<последний известный id>`. Пропущенные события
  сервер не хранит.
- В клиенте поток событий спрятан за `watchChats()` / `watchMessages()`: `ApiChatRepository` собирает из REST
  и событий те же списки, что отдаёт `FakeChatStore`.

### Пуш-уведомления

Этап 4. Сервер шлёт пуш на новое сообщение участникам, у которых нет активного WebSocket. Регистрацию токена
устройства и формат пуша опишем на этапе 4.

### Задел на этапы 2–4

`Message.kind`: `text`, `photo` (этап 2, `attachments` с `url`, `width`, `height`), `voice` (этап 3, `attachments`
с `url`, `durationMs`), `report` (этап 4, `reportId`), `system` (`systemEvent` и `subjectUserId`, текст формирует
клиент). Клиент этапа 1 показывает неизвестные ему виды как «Неподдерживаемое сообщение», поэтому сервер может
включать их раньше клиента.

## Error Format

Все ошибки возвращаются в формате:

```json
{
  "error": "Человекочитаемое описание ошибки"
}
```

### HTTP коды

| Код | Значение |
|-----|----------|
| 200 | Успех |
| 201 | Создано |
| 204 | Без содержимого |
| 400 | Ошибка валидации |
| 401 | Не авторизован |
| 403 | Нет доступа |
| 404 | Не найдено |
| 409 | Конфликт (дублирование) |
| 429 | Слишком много запросов (`Retry-After`) |
| 500 | Ошибка сервера |

### Коды ошибок клиента

Текст из `error` клиент пользователю не показывает: он попадает только в `Failure.message` для логов.
Что увидит пользователь, решает `FailureCode` (`lib/core/error/failures.dart`). `Api*Repository` выводит его
из HTTP-статуса и эндпоинта:

| Ответ | `FailureCode` |
|-------|---------------|
| Нет соединения, обрыв, ошибка DNS | `network` |
| Таймаут запроса | `timeout` |
| 400 | `validation` |
| 401 на `POST /auth/login` | `invalidCredentials` |
| 401 на остальных запросах | `sessionExpired` |
| 403 (в том числе чат, где пользователь больше не участник) | `forbidden` |
| 404 на `POST /auth/join` (код неизвестен, использован или истёк) | `invalidInviteCode` |
| 404 на остальных запросах | `notFound` |
| 409 (сейчас только `POST /auth/register` и `POST /auth/join`) | `emailTaken` |
| 429 (сейчас `POST /auth/join` и `POST /chats/:id/messages`) | `tooManyRequests` |
| 5xx | `server` |
| Всё остальное | `unknown` |

Если на одном эндпоинте понадобится различать несколько ошибок с одинаковым статусом, сервер должен добавить
в ответ машиночитаемое поле `code` (например, `{"error": "...", "code": "email_taken"}`), а клиент — новое значение
`FailureCode`.

## Enums

### UserRole
- `owner` — владелец компании
- `foreman` — прораб
- `worker` — строитель

### ProjectStatus
- `active` — объект в работе
- `paused` — приостановлен
- `finished` — сдан (завершён)

### ChatType
- `direct` — личный чат двух людей одной компании
- `project` — чат команды объекта

### MessageKind
- `text`, `photo`, `voice`, `report`, `system` — см. «Чат → Задел на этапы 2–4»

### MessageStatus
- `sent` — сообщение на сервере
- `read` — его прочитал хотя бы один другой участник
- `sending` и `failed` бывают только на клиенте, сервер их не присылает

### ChatSystemEvent
- `memberAdded` — `subjectUserId` добавлен в команду объекта
- `memberRemoved` — `subjectUserId` убран из команды объекта или удалён из компании
